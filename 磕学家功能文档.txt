## 🔴 必须修复（会导致崩溃 / 功能错误）

### 1. `ShipperMarkGunRestrictionMixin` 逻辑完全反了

```java
ShipperPlayerComponent shipperComp = ShipperPlayerComponent.KEY.getNullable(player);
if (shipperComp == null || !shipperComp.isShipperMomentActive()) {
    return;   // ← 不是嗑学家，直接放行
}
```

**问题**：这个 Mixin 想"阻止被磕 CP 的无辜者在磕学时刻捡左轮"。但 `ShipperPlayerComponent` 是**每个玩家都有的组件**，`getNullable(player)` 对**任何玩家**都返回非 null 组件（只是字段默认值）。所以：

- 被磕 CP 的玩家（`SHIPPER_MARK`）→ `isShipperMomentActive()` 在自己的组件里**永远是 false**（只有嗑学家本人会 set true）→ 直接 `return` 放行 → **限制完全失效**。

正确做法：应该查**嗑学家**的组件，不是被标记玩家自己的：

```java
@Inject(method = "canPickUpRevolver", at = @At("HEAD"), cancellable = true, require = 0)
private void pathsrole$blockInnocentShipperMarkPickupGun(Player player, CallbackInfoReturnable<Boolean> cir) {
    if (!(player.level() instanceof net.minecraft.server.level.ServerLevel serverLevel)) return;

    WorldModifierComponent wmc = WorldModifierComponent.KEY.get(serverLevel);
    if (wmc == null || !wmc.isModifier(player.getUUID(), ModModifiers.SHIPPER_MARK)) return;

    SREGameWorldComponent gameWorld = SREGameWorldComponent.KEY.get(serverLevel);
    if (gameWorld == null) return;
    SRERole role = gameWorld.getRole(player);
    if (role == null || !role.isInnocent()) return;

    // 找嗑学家的组件，而不是玩家自己的
    for (ServerPlayer sp : serverLevel.players()) {
        if (!gameWorld.isRole(sp, ModRoles.SHIPPER)) continue;
        ShipperPlayerComponent shipperComp = ShipperPlayerComponent.KEY.getNullable(sp);
        if (shipperComp != null && shipperComp.isShipperMomentActive()) {
            cir.setReturnValue(false);
            cir.cancel();
            return;
        }
    }
}
```

⚠️ 注意：如果本局可能有**多个嗑学家**（虽然 `setDefaultMax(1)`，但手动配置可能 >1），只要有一个在磕学时刻就限制；如果设计是"必须所有嗑学家都在磕学时刻"，改成"只要有一个不在就放行"。

### 2. `ShipperPistolItem` 客户端不发冷却包，但服务端加冷却；冷却时长不一致

```java
// 客户端：只发 GunShootPayload，本地不加冷却
if (world.isClientSide) {
    ... ClientPlayNetworking.send(...);
    spawnHandParticle();
} else {
    ... // 服务端什么都不做
}
user.getCooldowns().addCooldown(this, COOLDOWN_TICKS);   // ← 两端都会执行
```

`use()` 方法末尾的 `addCooldown` **两端都会跑**，所以冷却本身没问题。但对比 `ShipperMomentRevolverItem`：

```java
// ShipperMomentRevolverItem
if (world.isClientSide) {
    ...
    user.getCooldowns().addCooldown(TMMItems.REVOLVER, 20 * 20);   // 客户端加 TMMItems.REVOLVER 冷却
} else {
    ...
    user.getCooldowns().addCooldown(ModItems.SHIPPER_MOMENT_REVOLVER, 20 * 20);   // 服务端加自己
}
return InteractionResultHolder.consume(stack);   // 方法末尾没有 addCooldown
```

两个枪**冷却项不一致**：
- `ShipperPistolItem` 用 `this`（即 `SHIPPER_PISTOL`），冷却 120 tick；
- `ShipperMomentRevolverItem` 客户端加 `TMMItems.REVOLVER`，服务端加 `SHIPPER_MOMENT_REVOLVER`，冷却 400 tick。

如果玩家**手持 SHIPPER_MOMENT_REVOLVER 但客户端预测时**，客户端加的是 `REVOLVER` 冷却——**不阻止再次使用本物品**（因为 `isOnCooldown(SHIPPER_MOMENT_REVOLVER)` 客户端为 false，右键仍会发 `GunShootPayload`），只是服务端会拒绝。这会导致**客户端视觉/音效每 tick 都触发**。建议统一：

```java
// ShipperMomentRevolverItem 服务端也要像 ShipperPistolItem 一样在末尾加：
if (!world.isClientSide) {
    user.getCooldowns().addCooldown(this, 20 * 20);
}
// 客户端也加 this，不是 REVOLVER
```

### 3. `ShipperMomentRevolverItem` 的 `GunShootPayload` 服务端没有处理逻辑

看 `ShipperPistolItem` 和 `ShipperMomentRevolverItem`，客户端都发 `GunShootPayload(targetId)`。但**服务端谁处理这个 payload？** 源码里没有。通常 `GunShootPayload` 由 SRE 核心 mod 处理（发射子弹、命中判定）。如果核心 mod 只认 `TMMItems.REVOLVER` 作为武器，那么 `ShipperMomentRevolverItem` 发出的 payload 可能**不会造成伤害**——相当于玩家白开枪。

需要确认：`GunShootPayload` 的处理方（`io.wifi.starrailexpress.network.original.GunShootPayload` 的服务端 handler）是否按"玩家主手物品"判断武器类型？如果它检查 `mainHand.is(TMMItems.REVOLVER)`，那自定义枪**永远打不出伤害**。**这是功能性 Bug，必须在游戏里实测**。

如果确认无效，方案是：
- 服务端收到 payload 后，自己实现命中判定（`ProjectileUtil.getHitResultOnViewVector` + `GameUtils.killPlayer`）；
- 或让自定义枪 `use()` 时临时把主手替换成 `TMMItems.REVOLVER` 再调用（脏但可行）。

### 4. `ShipperFadeAlphaMixin` 的 `AlphaVertexConsumer` 不完整，且 `render` 递归调用可能死循环

```java
@Inject(method = "render", at = @At("HEAD"), cancellable = true)
private void pathsrole$fadeRender(...) {
    if (pathsrole$fading) return;   // ← 防递归，OK
    ...
    ci.cancel();
    try {
        ...
        renderer.render(entity, entityYaw, partialTick, poseStack, wrapped, packedLight);   // 递归调用
        ...
    } finally {
        pathsrole$fading = false;
    }
}
```

**问题 1**：`LivingEntityRenderer.render` 是**每个渲染帧每个实体**都调用的。对所有玩家（包括自己）都会走这条路径。如果 `comp.getInvisibilityAlpha()` 在客户端拿到的不是预期值（比如组件同步延迟），可能**所有玩家都半透明**。需要确认 `ShipperPlayerComponent` 是 `shouldSyncWith` 所有玩家（当前 `return true`，OK），且客户端能拿到 alpha。

**问题 2**：`AlphaVertexConsumer` 只实现了一部分 `VertexConsumer` 方法。1.21 的 `VertexConsumer` 接口有 `addVertex` / `setColor` / `setUv` / `setUv1` / `setUv2` / `setNormal` / `setLight` / `setOverlay`，这里都实现了。但**没有 `setColor(int)` 单参重载**（默认方法会调用 `setColor(int,int,int,int)`，OK）。看起来能用。

**问题 3（严重）**：`RenderSystem.enableBlend()` + 手动 `renderer.render` 后 `RenderSystem.disableBlend()`。如果 `renderer.render` 内部抛异常，`finally` 只重置 `pathsrole$fading`，**没有 `RenderSystem.disableBlend()`** → 渲染状态泄漏到后续实体。应把 `disableBlend` 也放 `finally`。

**问题 4**：`pathsrole$fading` 是**实例字段**，但 `LivingEntityRenderer` 是每个实体一个实例吗？不是——**每种实体类型一个 renderer 实例**。所以多个玩家共用同一个 renderer 实例，`pathsrole$fading` 会互相干扰。应改为**线程局部**或用 `poseStack` 栈深度判断。更简单：把 `pathsrole$fading` 改成 `ThreadLocal<Boolean>`。

建议重写：

```java
@Unique
private static final ThreadLocal<Boolean> PATHSROLE_FADING = ThreadLocal.withInitial(() -> false);

@Inject(method = "render", at = @At("HEAD"), cancellable = true)
private void pathsrole$fadeRender(...) {
    if (PATHSROLE_FADING.get()) return;
    if (!(entity instanceof Player player)) return;
    ShipperPlayerComponent comp = ShipperPlayerComponent.KEY.getNullable(player);
    if (comp == null) return;
    float alpha = comp.getInvisibilityAlpha();
    if (alpha >= 0.99f) return;
    if (alpha <= 0.01f) { ci.cancel(); return; }   // 完全透明直接不渲染

    PATHSROLE_FADING.set(true);
    ci.cancel();
    try {
        RenderSystem.enableBlend();
        RenderSystem.defaultBlendFunc();
        MultiBufferSource wrapped = new AlphaBufferSource(buffer, alpha);
        ((LivingEntityRenderer)(Object)this).render(entity, entityYaw, partialTick, poseStack, wrapped, packedLight);
    } finally {
        RenderSystem.disableBlend();
        PATHSROLE_FADING.set(false);
    }
}
```

**问题 5**：`LivingEntityRenderer.render` 在 1.21 有多个重载，`@Inject` 不带 `require` 时若签名不匹配会静默失败。建议加 `require = 1`（强制校验），否则调试时根本不知道 Mixin 没生效。

### 5. `ShipperInvisibleMixin` 对**所有实体**都注入 `isInvisible`

```java
@Mixin(Entity.class)
public class ShipperInvisibleMixin {
    @Inject(method = "isInvisible", at = @At("RETURN"), cancellable = true)
    private void pathsrole$fadeIsInvisible(CallbackInfoReturnable<Boolean> cir) {
        ...
        if (!(entity instanceof Player player)) return;
        ShipperPlayerComponent comp = ShipperPlayerComponent.KEY.getNullable(player);
        ...
    }
}
```

每个实体的 `isInvisible()` 调用（包括**每 tick 的 AI 判定、每个实体的渲染判定**）都会触发这个 Mixin。虽然提前 `return` 了非玩家，但 `KEY.getNullable` 对玩家是 CCA 查询，**每 tick 每玩家调用多次**，有性能开销。

更严重：`isInvisible()` 在**服务端**也会被调用（比如怪物是否攻击玩家）。`ShipperPlayerComponent.KEY.getNullable` 在**非 CCA 注册的端**会返回 null，但 `KEY.getNullable` 在服务端是正常的。问题是——**半透明（alpha 0.5）的玩家在服务端 `isInvisible()` 返回 false，但客户端应该"看得到但半透明"**。而 `isInvisibleTo` 被设为 true 时，**客户端会跳过渲染该玩家**（vanilla 逻辑），导致半透明根本没机会渲染。这两个 Mixin 会互相打架：

- `ShipperInvisibleMixin` 设 `isInvisible()=true`（当 alpha ≤ 0.01）
- `ShipperFadeAlphaMixin` 想用 `alpha` 渲染半透明

当 alpha 在 0.01~0.99 之间时，`isInvisible()` 返回 false（正常），`ShipperFadeAlphaMixin` 生效——OK。
当 alpha ≤ 0.01 时，`isInvisible()` 返回 true，**客户端直接不渲染**，`ShipperFadeAlphaMixin` 的 `alpha <= 0.01` 分支也 `ci.cancel()`——**两个都对，OK**。

但 `isInvisibleTo(Player observer)` 被设为 true 时，**observer 看不到该玩家**。问题：**旁观者（spectator）也该看不到吗？** 通常隐身对旁观者无效。建议 `isInvisibleTo` 里加 `if (observer.isSpectator()) return;`。

### 6. `ShipperEvents.findDeadShipperComponent` 实际找的是**在线**嗑学家

上一轮已提过，这次结合 `checkShipperGameEnd` 再看：

```java
List<? extends Player> remainingPlayers = serverWorld.getPlayers(p -> isPlayerAliveAndSurvival(p) && !isRole(p, REIMU));
ServerPlayer shipperPlayer = null;
for (Player player : remainingPlayers) { if (isRole(player, SHIPPER)) { shipperPlayer = ...; break; } }

    ShipperPlayerComponent deadShipperComp = findDeadShipperComponent(serverWorld);   // 但 players() 只含在线
    ...
}
```

`serverWorld.players()` 是**在线玩家列表**（含已死但未退服的）。如果嗑学家**活着但被排除**（比如是 REIMU，不可能同时是 SHIPPER）或**已死但还在服务器**，`findDeadShipperComponent` 能返回。如果嗑学家**断线**，返回 null → 恋人无法判胜。这可能是设计限制，但方法名"Dead"极其误导。建议改名为 `findAnyShipperComponentOnline`，并加注释"仅在线"。

### 7. `ShipperMarkClientHandler` 里两个 `CommonHudRenderCallback` 重复遍历 + 逻辑错位

第一个回调：给恋人显示"另一半的名字 + 角色"。
第二个回调：显示"成为恋人 HUD"提示，带淡出。

两者都在 `for (Player p : player.level().players())` 里找嗑学家，且都 `break`。但注意第二个回调的 `break` 逻辑：

如果找到**第一个嗑学家**但该嗑学家的 `pairingTime` 不满足条件（比如 < 10s），`break` 直接退出，**不会检查后面的嗑学家**。多嗑学家场景下 HUD 可能不显示。改为 `continue` 而非 `break`（但要避免多嗑学家同时显示冲突，需要明确设计）。

### 8. `ShipperBookScreen.loadMarkedPlayers` 的 `isTouristMode` 逻辑有 bug

```java
private void loadMarkedPlayers() {
    ...
    ShipperPlayerComponent comp = KEY.get(this.minecraft.player);
    if (comp != null) {   // ← 任何玩家都有 comp（CCA 组件默认存在）
        for (UUID uuid : comp.getPairedLovers()) { ... }
        if (this.markedPlayerNames.isEmpty() && comp.hasEverBound()) { ... }
        return;   // ← 直接返回，永远不会走 tourist 分支
    }
    this.isTouristMode = true;   // ← 死代码
    ...
}
```

`ShipperPlayerComponent.KEY.get(player)` 对**任何玩家**都返回非 null（CCA 组件是懒加载的）。所以 `comp != null` 恒成立，`isTouristMode = true` **永远不执行**。结果：非嗑学家拿嗑学家书（游客模式）时，`markedPlayerNames` 为空，书里显示"无玩家"而不是读取 NBT 的 A/B 名字。

**修复**：判断的是"当前玩家**是不是嗑学家**"，不是"组件是否存在"：

```java
private void loadMarkedPlayers() {
    this.markedPlayerNames.clear();
    if (this.minecraft == null || this.minecraft.player == null) return;

    boolean isShipperRole = SREClient.gameComponent != null
        && SREClient.gameComponent.isRole(this.minecraft.player, ModRoles.SHIPPER);

    if (isShipperRole) {
        ShipperPlayerComponent comp = KEY.get(this.minecraft.player);
        if (comp != null) {
            for (UUID uuid : comp.getPairedLovers()) {
                this.markedPlayerNames.add(getPlayerNameWithRole(uuid, comp));
            }
            if (this.markedPlayerNames.isEmpty() && comp.hasEverBound()) {
                this.markedPlayerNames.addAll(comp.getAllPlayerNames());
            }
            return;
        }
    }

    // 游客模式：读 NBT
    this.isTouristMode = true;
    ItemStack stack = this.minecraft.player.getMainHandItem();
    if (!stack.is(ModItems.SHIPPER_BOOK)) stack = this.minecraft.player.getOffhandItem();
    if (!stack.is(ModItems.SHIPPER_BOOK)) return;
    ...
}
```

### 9. `ShipperBookItem.storePlayerName` 与 `ShipperEvents.handleShipperBookUse` **两套配对逻辑冲突**

`ShipperBookItem` 客户端 `use()`：
- 右键生物 → `storePlayerName(stack, targetName)`，写入 **NBT 的 PlayerA/PlayerB**（游客模式用）；
- 右键空气 → `openBookScreen`。

`ShipperEvents` 服务端 `UseEntityCallback`：
- 右键生物 → `handleShipperBookUse` → `bindLovers`（**真正的角色配对**）。

两者**同时对"右键生物"做处理**。`UseEntityCallback` 的返回 `InteractionResult.FAIL` 会阻止客户端 `use()` 吗？**不会**——`UseEntityCallback` 是服务端事件，客户端 `ShipperBookItem.use()` 会**先执行**（客户端预测），再被服务端的 `UseEntityCallback` 覆盖。结果：

- 客户端：写 NBT PlayerA/PlayerB（**改动物品 NBT**）
- 服务端：`bindLovers`（改 WorldModifierComponent）

**NBT 数据和服务端配对数据不一致**。如果玩家是真正的嗑学家，NBT 的 PlayerA/B 会一直累积，且**服务端不读 NBT**，这些数据纯属垃圾。如果玩家是游客（非嗑学家），`ShipperEvents.handleShipperBookUse` 会 `isRole(shipper, SHIPPER)` 检查失败直接 return，客户端 NBT 生效——**游客模式是唯一有效场景**。

**建议**：`ShipperBookItem` 客户端 `handleClientUse` 里加判断，**只有非嗑学家角色才写 NBT**：

```java
private void handleClientUse(ItemStack stack, Player user) {
    ...
    if (targetPlayer instanceof Player) {
        // 真正的嗑学家由服务端 UseEntityCallback 处理，客户端不写 NBT
        var gameComp = SREClient.gameComponent;
        if (gameComp != null && gameComp.isRole(user, ModRoles.SHIPPER)) {
            return;
        }
        ...游客逻辑...
    }
}
```

### 10. `ShipperBookScreen.init()` 每次打开都 `loadTemplates` + `loadMarkedPlayers` + `regenerateText`，但 `init` 可能被多次调用

`Screen.init()` 在窗口 resize 时会被重新调用。`regenerateText` 用 `new Random()` 随机模板 → **每次 resize 文本都变**。建议把 `regenerateText` 的结果缓存，或在 `init` 里只调一次（用标志位）。

### 11. `CupidPlayerComponentMixin` 里 `preventCannotBeLoverRolesFromBeingMarkedOrLinked` 的 `markedPlayer` shadow 可能与实际字段名不符

```java
@Shadow

```

如果 `CupidPlayerComponent` 里的字段实际叫 `markedPlayerUUID` 或 `loverUUID`，编译期不报错（`@Shadow` 在编译期不校验），**运行时 Mixin 应用失败**。需要确认字段名。此外 `@Shadow public abstract void clearMark();` 如果 `clearMark` 不是 `public` 会失败。

### 12. `SREMurderGameModeMixin` 可能不生效

```java
@Inject(method = "allowGameEnd", at = @At("HEAD"), cancellable = true)
```

如果 `SREMurderGameMode.allowGameEnd` 是 **private** 或签名不同（比如参数顺序），Mixin 会**静默失败**（没有 `require = 1`）。而且这个方法如果被多个 mod 也 Mixin 了，`HEAD` 注入的顺序不确定。建议加 `require = 1` 并在测试环境确认日志有 Mixin 应用记录。

## 🟠 建议修复

### 13. `ShipperPlayerComponent.setShipperMomentActive(false)` 会没收胜利方的枪

`handleShipperMomentWinCheck` 里：
```java
RoleUtils.customWinnerWin(...);
shipperComp.setShipperMomentActive(false);   // ← 触发 retrieveMomentRevolvers，没收恋人的枪
```

如果"胜利后回收枪"是设计意图（防止下一局残留），OK；否则应在 `OnGameEnd` 统一回收，不要在胜利判定里做。**建议加注释**。

### 14. `ShipperPlayerComponent.clearRage()` 把 `observationActive` 设为 `true`

```java
public void clearRage() {
    ...
    this.observationActive = true;   // ← 自动开启观察模式？
    this.observationCooldownEnd = System.currentTimeMillis() + 60_000L;
    this.sync();
}
```

**"怒气结束自动开启观察"** 这个设计很奇怪——玩家可能不想开。而且 `observationCooldownEnd` 设 60s，意味着**接下来 60s 玩家不能主动开/关观察**（`toggleObservation` 检查 cooldown）。这会卡住玩家技能。建议改为 `observationActive = false` 并清 cooldown，或加注释说明这是有意设计。

### 15. `ShipperEvents.handleShipperMomentLinkedDeath` 里嗑学家死亡时杀恋人的逻辑，与 `handleShipperDeath` 重复

`OnPlayerDeath` 里：
```java
handleShipperMomentLinkedDeath(deadPlayer, gameWorld);   // 若 isShipper && momentActive → 杀恋人
if (isRole(deadPlayer, SHIPPER)) handleShipperDeath(deadPlayer);   // momentActive → setShipperMomentActive(false) 并 return
handleLoverDeath(deadPlayer);   // 若 deadPlayer 是恋人 → 杀另一个
```

嗑学家死亡时：
1. `handleShipperMomentLinkedDeath` → 杀所有恋人 → `clearPendingBetrayalKiller` → return
2. `handleShipperDeath` → `isShipperMomentActive()` 若 true → `setShipperMomentActive(false)` → return（不加护甲）
3. `handleLoverDeath` → deadPlayer 不是恋人（是嗑学家）→ `findShipperComponent(deadPlayer)` 返回自己的组件 → `isMarked = false`、`isPaired = false` → return

**注意**：步骤 1 里 `handleShipperMomentLinkedDeath` 的 `isShipper` 分支**不 `setShipperMomentActive(false)`**，步骤 2 才设。所以步骤 2 的 `setShipperMomentActive(false)` 会触发 `retrieveMomentRevolvers`——此时恋人已死，`getPlayerByUUID` 返回的玩家 `isAlive()=false`，跳过。枪留在恋人尸体背包。**这是边界行为**，如果尸体生成后物品掉出，枪可能被其他人捡走。建议 `retrieveMomentRevolvers` 里不检查 `isAlive()`，直接清背包（死人背包也能清）。

### 16. `ModModifiers` 里 `REIMU_CURSE` 的 `UNLUCK` 只加一次

```java
if (!BLINDNESS_APPLIED_PLAYERS.contains(player.getUUID())) {
    player.addEffect(new MobEffectInstance(MobEffects.UNLUCK, 200, 0, false, false, true));
    BLINDNESS_APPLIED_PLAYERS.add(player.getUUID());
}
```

变量名叫 `BLINDNESS_APPLIED_PLAYERS`，但实际加的是 `UNLUCK`（不是 BLINDNESS，前面加的是 MOVEMENT_SLOWDOWN）。**命名错误**。而且 `UNLUCK` 只加 200 tick（10s），之后不会再加——如果诅咒持续整局，UNLUCK 应该每 200 tick 刷新一次，或改成 `999999`。当前逻辑是"第一次 tick 加 10s UNLUCK，之后永远不加"，**玩家 10s 后就没 UNLUCK 了**。Bug。

### 17. `ModRoles.SHIPPER.onAbilityUse` 与 `ShipperEvents.registerSkills` 重复

两处都注册了"观察模式切换"能力：
- `registerSkills` 里 `RoleSkill.skill(id("shipper_book"), ...)` → `toggleObservation`
- `ModRoles.SHIPPER.onAbilityUse` 里又写了一遍 `toggleObservation`

如果 `RoleSkill` 和 `onAbilityUse` 是两个独立的触发路径（比如一个是 HUD 技能，一个是右键书），可能重复触发。**建议确认是否需要两套，否则删掉一个**。

### 18. `ShipperShopHandler` 只有 1 个商品，且 `getEntries()` 可能返回 null

```java
private static List<ShopEntry> entries;
public static void init() { entries = List.of(...); }
public static List<ShopEntry> getEntries() { return entries; }
```

如果 `init()` 没被调用（比如注册顺序问题），`getEntries()` 返回 **null**，商店 UI 可能 NPE。建议 `entries = List.of()` 初始化默认空列表。

### 19. `ShipperMomentRevolverItem` / `ShipperPistolItem` 的 `onUseGun` 检查了两端

```java
if (world.isClientSide) {
    if (gameComponent != null) {
        if (!role.onUseGun(user)) return fail;   // 客户端检查
    }
} else {
    if (gameWorldComponent != null) {
        if (!role.onUseGun(user)) return fail;   // 服务端检查
    }
}
```

`onUseGun` 如果**有副作用**（比如消耗资源），两端都调会**双倍消耗**。如果只是权限判断，OK。需确认 `SRERole.onUseGun` 的实现。
